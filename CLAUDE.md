# Minideas

Static, bilingual (English / Vietnamese) site of illustrated explainers and book reviews, at https://minideas.com. The repo is public and open to contributions (`CONTRIBUTING.md`); code is MIT, writing and drawings CC BY-NC 4.0 (`LICENSE-CONTENT.md`). The owner's product notes (`minideas.md`), planning notes and source decks are local only, ignored by git: never commit them.

## Commands

- `npm run build`: builds everything into `dist/` (pages, sketch drawings, preview images, photos). Sketches and preview images are cached in `node_modules/.cache/og/`, so a rebuild takes about a second; a cold build takes about 40s.
- `npm run dev` (or `npm run preview`): serves `dist/` at http://localhost:4321, rebuilds when `src/` or `build.mjs` changes, and reloads open pages. The owner keeps it running: **never kill port 4321**. To check changes, wait for the rebuild and screenshot http://localhost:4321 with `?noreload` (the reload connection never settles, so headless Chrome would hang); for one-off pages, write them into `dist/` (the next rebuild removes them). Don't run `npm run build` while the dev server is running: both builds delete `dist/` and can leave it half empty. Edit `src/`, then wait for the rebuilt file to appear. To see build errors without touching `dist/`, build somewhere else: `OUT_DIR=<scratch folder> node build.mjs`.
- The site address defaults to https://minideas.com (absolute `og:image`, canonical and hreflang links). Override it with `SITE_URL=https://… npm run build`, e.g. for a `workers.dev` test deploy.
- **Hosting:** Cloudflare Workers, static assets only (`wrangler.jsonc`: serves `dist/`, `404.html` for missing pages). The `minideas` Worker builds from GitHub, so **every push to `main` goes live** on minideas.com within about a minute. Work happens on the `dev` branch, which Cloudflare doesn't build; merge into `main` only to publish, so the site rebuilds once per batch of changes. `www.minideas.com` redirects to minideas.com (a Cloudflare redirect rule, not in the repo).
- `node build.mjs --explicit-index`: links end in `index.html`, for hosts without directory indexes.
- Newsletter drafts: the build also writes `node_modules/.cache/newsletter.html` (outside `dist/`, never deployed), ready-to-paste Kit emails for the newest stacks in each language; the dev server shows it at http://localhost:4321/newsletter/.
- `node tools/import-review.mjs <id> <slug>`: turns a Sâu Sách review into `src/books/<slug>/full.js`.

There are no tests. The build is the check: it stops and lists problems (missing text in a language, panel or section counts that don't match, drawings that output `undefined`/`NaN`, missing photos or captions, duplicate names). Never edit `dist/`; it is deleted on every build.

## How content is organised

- **Topics live in folders.** `src/tech/<id or slug>/` (named after the home page's Tech shelf) holds one tech topic: `stack.js` (its shape: either a **collection**, `id`, `chapters`, `resources`, `ideas`, or a **standalone idea**, `slug`, `panels`, `resources`; the folder is named after it), `draw.js` (its drawings), and `en.js` / `vi.js` (its words). `src/tech/index.js` holds `SHELF`, the home page "Tech" (Công nghệ) shelf in order, as a list of folder names; a folder not listed isn't published. Books form the "Books" (Sách) shelf. Shelf icons are `SHELF_ICONS` in `src/build/icons.js`. Any item, and any book, can name one `related` stack (a slug on either shelf), shown as a card at the end; a collection's shows after its last idea. Each panel is `[drawingName, ...args]` pointing at a drawing in the topic's `draw.js`. `src/content.js` loads the folders, gathers every drawing into `ART` and each language's words into one table, and stops the build on a name used twice (drawings, ideas and label groups share one namespace across all topics and books).
- A topic's `en.js` / `vi.js` export `collections[id]` (if it is a collection), `ideas[slug]` (title, gist, one `[heading, text]` per panel, `links` for a standalone idea's resources) and `art`, the labels used inside its drawings. A topic is published in each language that has its words. An idea title that starts with its chapter's name ("Claude Code: getting started") loses that prefix where the chapter is already shown: the collection page, the contents list and the idea's heading (`titleIn` in `src/build/pages.js`); the tab, link preview, pager and feed keep the full title. Keep each topic's en and vi files line-aligned, so they can be read side by side. `src/i18n/en.js` and `src/i18n/vi.js` hold only the site's own words (`ui`).
- `src/books/<slug>/` is a book, listed in order in `src/books/index.js` (a folder not listed isn't published: The Hobbit and The Second World War wait there). `book.js` is the card stack of `panels` (one per idea of the review, with `vi` / `en` text). It can carry the full review in `full` (imported from `full.js`, an article: intro, sections, quotes, conclusion, gallery), published at `/<lang>/<slug>/full/`. `draw.js` holds the book's drawings, `photos/` the reviewer's photos. A book in only one language (`vi` or `en`) appears only on that language's site.
- `src/draw.js` is the drawing vocabulary: the helpers every topic's and book's `draw.js` builds from (`T`, `L`, `C`, `R`, `P`, `A`, `pill`, `fig`…), plus small pictures several topics share. A helper or running example only one topic uses stays in that topic's `draw.js`. Every drawing is a 320×220 SVG fragment and receives the language's label table as `lb`.
- Drawings appear as **pencil sketches**. `src/sketch.js` renders a drawing's shapes at build time with resvg (pencil filter, coloured-pencil fills, the theme's paper; dark is lighter, like chalk) and sharp encodes them as WebP, one per theme, into `/sketch/<hash>-<theme>.webp` (named after the shapes, so a drawing that looks the same in both languages is one file). The labels stay real text on top, so readers can copy them. In a card stack the picture is a CSS background, so every card shows at once and only the current theme's one downloads (lazy images in the sideways scroller stayed blank); tiles and full-review drawings use a pair of lazy images. The shape colours live in `THEMES` in `sketch.js`, copied from the tokens in `style.css`: change both together.
- `src/og.js` renders 1200×630 PNGs with resvg: one per page (home, idea, collection, book), used as link previews. Each has the logo and site name, the title, the page's summary (gist, collection lede or book abstract), where it sits ("Bài 5/15 · Nền tảng AI", "15 bài", the author) and the first panel as a light-theme pencil sketch, or the book's cover. The home page's preview is the logo, the tagline and three stacks picked by hand (`HOME_PREVIEW` in `src/build/config.js`: AI Fundamentals, The Shallows, Graph databases), so it shows both shelves and doesn't change with each new stack. After changing a published preview, use "Scrape Again" in the Facebook Sharing Debugger.
- `build.mjs` runs the build: check the content, make every page, write them with the assets and pictures. Its parts are in `src/build/`: `config.js` (site address, output folders, the Kit and Web3Forms ids, `HOME_PREVIEW`), `checks.js` (everything that stops a build), `pages.js` (home, collection, idea, book pages), `site-pages.js` (follow, confirmed, suggest, 404, root), `layout.js` (the page shell and shared pieces), `pictures.js` (sketches and preview images, with their cache), `feed.js` (RSS, newsletter drafts), `shelves.js` (derived lists, book photos, dates) and `icons.js`. It produces pages at `/<lang>/`, `/<lang>/<collection>/` and `/<lang>/<slug>/`. Collections, ideas and books share one URL namespace. Paths are the same in every language, only the `/<lang>/` prefix differs: don't translate slugs (a book's full review is `/<lang>/<slug>/full/`, never `/vi/<slug>/day-du/`). It also writes an RSS feed per language (`/<lang>/feed.xml`), a Follow page (`/<lang>/follow/`: the email sign-up, which posts to that language's Kit form, `KIT_FORMS` in `src/build/config.js`, then one line with the feed's address; browsers don't display feeds, so the site links here), a "You're subscribed" page where Kit sends readers after they confirm (`/<lang>/follow/confirmed/`, kept out of the sitemap), plus `404.html`, `sitemap.xml`, `robots.txt` and `_redirects` (Cloudflare reads it and doesn't serve it). A live page's slug changes only with an entry in `MOVED` (`src/build/config.js`, old slug → new slug), which redirects the old address in every language so shared links keep working; the old slug then stays reserved (`next-word` became `how-chatbots-write`). The newsletter is Kit's free plan: one form per language, emails sent by hand from the drafts page (see Commands). `/<lang>/suggest/` is the "Suggest or send an article" form (Gợi ý hoặc gửi bài) that Web3Forms emails to the owner: a topic, plus optionally a link to something the reader wrote, which is how contributors without GitHub send articles; a note under it links to CONTRIBUTING.md for the GitHub way (`SUGGEST_KEY` in `src/build/config.js`; the key is public by design). `home`, `follow` and `suggest` can't be used as slugs.
- `src/assets/icon.svg` is the logo: a lightbulb whose filament is a lowercase "m". The build turns it into `favicon.svg`/`.ico`/`-32.png`, `apple-touch-icon.png`, `icon-192/512.png` and `site.webmanifest` at the site root. `brand/` holds a copy and a 1024px profile picture for social accounts. The header logo is a different mark, a small card stack with the same "m" bulb, drawn in `src/build/icons.js` (`BRAND_MARK`) with theme colors.
- `ideas/` is source material (PDFs, the Sâu Sách backup and export, photos). It is not part of the site. Only the Sâu Sách export and a Neo4j cheat sheet are in the repo; the rest is ignored.

## Adding things

- **Idea:** add it to its topic's folder: panels in `stack.js`, the words in `en.js` / `vi.js`, any new drawing in `draw.js`. A new topic is a new folder in `src/tech/` (copy a small one, `graph-databases`) plus its name in `SHELF`. A collection or idea is published in each language that has its text (`collections[id]` or `ideas[slug]`), so a contributor can write one language and the other is translated later; a collection in a language needs all its ideas in it. Duy's own stacks go out in both languages. `docs/adding-content.md` is the contributors' walkthrough: keep it in step when the content format changes.
- **Dates:** every page shows when it was published. Collections and standalone ideas carry `date` (YYYY-MM-DD) in their `stack.js`. A collection's date shows on its own page, not on each idea in it. Books take `date` from the full review (the Sâu Sách publish date, `reviewedDate` in the export); a book without one uses `added`, and a full review shares its card stack's slug, author, date and cover unless it sets its own. Books also carry `added`, the day they went on Minideas, which orders the RSS feed. Anything added after launch day (the earliest `date`/`added`) gets a "New" mark on its home tile for 14 days. Set the Tech dates and the books' `added` to the launch day when you publish. Full reviews also show reading time (`wordsPerMinute` in `ui` in `en.js` / `vi.js`).
- **Book review:** run the importer, which writes the full review to `src/books/<slug>/full.js`. Then write the card stack in `book.js` next to it (see `src/books/outliers/book.js`) and add the slug to `BOOKS`: one panel per idea, each 2–3 sentences condensed from the reviewer's text, with a drawing or `["photo", file]`. It reuses the full review's labels and captions. Copy the photos from the review's folder in `ideas/sausach/Images/` (the `PhotosFolder` of the review, or a folder named after the book) into `src/books/<slug>/photos/` without their metadata, set `cover` and the full review's `photos` gallery, and add a caption per language for each photo. Section pictures in the full review are optional: `art.sections: { <section number>: [drawing] }` with labels in `vi.labels` / `en.labels`, or `["photo", file]` for a picture the review showed at the start of that section. A picture the review put between paragraphs is a `{ photo: file }` block at that spot in `intro` or a section's `body`. Either way it leaves the gallery. New books can be card-stack only. Re-running the importer overwrites `full.js`, so it undoes hand edits there: The Shallows' Vietnamese `title` was changed by hand to match the cover ("Trí tuệ giả tạo: Internet đã làm gì chúng ta?").
- After visual changes, render and look at them. For drawings, put every panel on one contact sheet and screenshot it with headless Chrome: a page in `dist/` that loads `/assets/style.css`, fetches the built idea and book pages and copies out the contents of each `.slide .art` and `figure .art` works well (set its `data-theme` to check both themes). For pages, screenshot at about 1100px and 390px wide (use an iframe for 390px, because headless Chrome enforces a minimum window width). Check Vietnamese too: its labels run longer. Don't combine an iframe with `--virtual-time-budget`, which can hang Chrome. macOS has no `timeout`, so run Chrome in the background and kill it after about 40s.

## Writing explainers

Explainers are for a **general curious reader**, not for exam prep or vendor training. AI Fundamentals started as a mirror of the owner's slide deck (one idea per slide, in slide order, chapters taken from the deck's section headers) and had to be rewritten. When the source is slides or a course:

- **Build a learning path, not a slide order.** Each idea should rely only on earlier ideas. Before ordering, ask what a reader must already know for each panel. For example, regression has to come before the house-price error plot, prompting before "customize a model", and next-word prediction before foundation models.
- **Connect ideas explicitly.** Refer back by title or by the example ("the same trick as the line through the house dots"), and point forward when a later idea builds on this one. Reuse a running example where you can, instead of a new one every time.
- **Cover what readers actually wonder about**, even if the source skips it. For AI that meant "how does a chatbot write?" and "why does it make things up?".
- **Drop vendor material:** product catalogues, company or logo lists, and a vendor's own frameworks or terms (e.g. AWS's eight Responsible AI dimensions). They date quickly and aren't ideas.
- **Concrete scenes beat definition lists.** A panel that defines three terms in a row reads like a glossary. Show one situation instead: a hiring model copying past bias, a loan denied with no reason given.
- **Jargon once:** plain words first, then "experts call this X". Don't stack several terms in one panel.
- **No claims that date**, such as "most AI today is…" or market-share charts.
- **Balance chapters.** A chapter with a single idea usually means the grouping came from the source, not from the reader's needs.
- The first panel of each idea is also its home tile and share image, so it should stand on its own.

## Vietnamese text

Write Vietnamese the way a Vietnamese tech writer would, not as a word-for-word translation of the English. Translated titles are the most common slip:

- **Titles:** "Gia đình AI" (The AI family) → "Phân biệt AI, học máy, học sâu". "Biến mô hình thành của bạn" (Making a model yours) → "Tùy chỉnh mô hình cho riêng bạn". "Quy tắc và học hỏi" → "Lập trình truyền thống và học máy".
- **Words that mean something else:**
  - "ý tưởng" is an idea you come up with, not a topic you learn. The site calls an idea in a collection "bài" (Bài 3/15, 15 bài).
  - "máy tính tí hon" means tiny computers, not calculators.
  - "kỹ tính" describes a fussy person.
- **Use familiar idioms when they fit:** "học vẹt" (overfitting), "rác vào, rác ra", "nói chắc như đinh đóng cột", "thi được mở tài liệu" (open-book exam).
- **Technical terms:** give the Vietnamese term, then the English in brackets the first time: "quá khớp (overfitting)", "ảo giác (hallucination)". Terms used so far:
  - học máy, học sâu, AI tạo sinh, mô hình nền tảng
  - huấn luyện, huấn luyện thêm (fine-tuning), trọng số, embedding (vector nhúng), token
  - định kiến (bias against people), độ chệch / phương sai (model bias / variance)
  - code, not "mã" (which readers take as mã giảm giá, mã OTP): "code sạch", "viết code", "review code"; tái cấu trúc (refactoring)
  - file, not "tệp", which reads like a translated interface: "mở file", "sửa files"
- **English words keep the English plural.** An English noun in Vietnamese text takes "s" when it means more than one, as it would in English: "các files", "2.000 files", "hàng chục skills", "gộp skills, subagents, hooks và MCP servers", titles like "Skills: …". It stays singular after "mọi", "mỗi", "từng" and "một" ("mọi file", "mỗi skill"), as English says "every file".
- **Introduce a term plainly**, without crediting a group: "Đó chính là tái cấu trúc (refactoring)", "theo nguyên tắc DRY (…)", "Nguyên tắc này có tên là YAGNI (…)". "Giới lập trình gọi đây là…", "Dân lập trình…" and "Lập trình viên hay nhắc nhau…" sound stiff or forced, especially when repeated within one idea.
- **Check that short labels can't be misread.** "không có lý do để kiểm tra" was meant as "no reason anyone can check" but reads as "there's no reason to check". "Máy học như thế nào" collides with "máy học", a common name for machine learning, so use "Máy tính học…".
- **Keep cross-references in step.** When an idea's title changes, search every topic's `en.js` / `vi.js` (`src/tech/`) and the books for other text that quotes it.

## Drawing pitfalls

- CSS class rules override SVG presentation attributes, so `T()` sets font size as an inline `style`. Don't switch it back to `font-size="…"`.
- Use `T(..., { max: width })` for any label that may run long in Vietnamese; it shrinks the font to fit. Use `\n` for line breaks.
- Labels that sit on top of lines or dashed outlines need the `halo` class, or the line looks like a strikethrough.
- `pill()` turns narrow boxes into circles. For word chips, use `R(..., 6)` plus `T`, and allow about 0.52 em per character (Vietnamese diacritics included) so text clears the edges.
- resvg (share images) handles `<g transform="rotate(…)">`, e.g. for a tilted stamp.
- Text on pastel fills needs the `on` class (dark in both themes). Every color is a token in `style.css`, with light and dark values (the sketches' shape colours are copied into `sketch.js`).
- Patrick Hand has no ← → glyphs. Browsers fall back per character, but resvg switches the whole label to another font, so `og.js` swaps arrows for ASCII. If you add other special characters to labels, check them against the font's cmap with fontTools.
- Fonts must cover Vietnamese: Bricolage Grotesque (display), Lexend (body), Patrick Hand (drawings). The TTFs in `src/fonts/` are only for resvg; pages load the fonts from Google Fonts.

## Owner preferences

- **From Sâu Sách, only the owner's (Duy's) reviews, non-fiction only.** Sâu Sách had several reviewers, and the export doesn't say who wrote what (the backup does: `Reviews.ReviewerID` → `AspNetUsers.DisplayName`). Duy's published reviews are ids 1, 2, 3, 6, 22, 26, 29, 43 and 46; of those, 29 (The Hobbit) and 46 (The Alchemist) are fiction. Never import another member's review. New reviews that contributors write themselves are welcome, in their own structure and voice, with a rating if they want one.
- **Book reviews keep the reviewer's own words** (Duy's or a contributor's): their sections, paragraphs and quotes, in their order. Card-stack panels condense that text and add nothing. Don't write new opinions, verdicts, comparisons or reading-time claims. English versions are faithful translations, with a note that quotes are translated back from the Vietnamese edition. Point out typos in the original, but don't fix them silently.
- **No scores or ratings** in Duy's reviews or anywhere else on the site; a contributor may put one in their own review.
- **Books lead with the short card stack**, with one tile per book on the home page, and the full article one tap away. The full article shows the pictures the reviewer put in the text inside their sections (`art.sections: { <n>: ["photo", file] }`), in place of a drawing; sections without one may get a drawn illustration. All the reviewer's other photos go together in one gallery before the conclusion, never scattered through the text. Any photo from the review's folder can be used, including publisher cover scans, the author's portrait and the author's own illustrations. The front cover is the usual `cover` (header, tile and share image), and the gallery should include every photo the owner picks, so ask before leaving one out.
- **"Go deeper" links** must be publicly accessible. No login-gated or vendor training portals. A free course is fine when its page opens without an account, even if taking it needs one (Coursera, DeepLearning.AI).
- **Keep it simple:** static files, no database, no runtime dependencies. The only packages are build-time: `@resvg/resvg-js` (preview images, sketch drawings) and `sharp` (encodes the sketch drawings as WebP).
- **Home page stays compact:** one tile per collection, standalone idea or book. A collection's ideas are listed on its own page. Put a new stack first on its shelf (`SHELF` and `BOOKS` are in display order). When the last row would hold one tile alone, the first tile takes the whole row, with its picture beside the words (`.shelf-grid` in `style.css`).
- Vietnamese text should be checked by a native speaker before launch.

## Data and privacy

`ideas/sausach/SauSach2.bak` is a SQL Server 2012 backup that includes member emails and password hashes. Never publish it or copy member data into the site. `ideas/sausach/sausach-reviews.json` is the export used by the importer: Duy's published reviews only (the ids above), book and review fields only. The repo is public, so keep other members' reviews out of it. To re-export, restore the backup into a temporary `mcr.microsoft.com/mssql/server:2022-latest` container (`--platform linux/amd64`, backup folder mounted read-only), query the `Reviews` (including `ReviewedDate`, exported as `reviewedDate`), `Authors`, `Publishers` and `Genres` tables, then remove the container.
